# API integration

Three APIs meet in this project:

1. the **Alarm Management API** (the source system), built as a simulator from the assignment's Postman
   collections;
2. the **Alarm API connector**, the typed client the MCP server uses to call it;
3. the **copilot backend API**, which the GUI calls.

The MCP tools in between are documented in [mcp-tool-catalog.md](mcp-tool-catalog.md).

## 1. The Alarm Management API

The assignment provides the API only as Postman collections, so `services/alarm-simulator` implements it with
FastAPI and serves synthetic but realistic plant data. The collections are the contract: every endpoint,
request schema, response structure, authentication header, trace header and chaining flow follows them.

| | |
|---|---|
| Start | `uv run python -m alarm_simulator` (port 8000), or the `alarm-api` Docker service |
| Settings | `SIM_API_TOKEN` (default `demo-token`, the public token in the Postman collections), `SIM_PORT`, `SIM_LOG_LEVEL` |
| Data | `services/alarm-simulator/data/seed_data.json`: 3 sites, 19 assets, 24 alarm types, 423 alarms (1 April to 1 July 2026), generated by `seed/generate_seed.py` with seed 42 |

### Contract validation

The collections are kept in `test-data/postman/`. The baseline collection (15 requests, one per endpoint) and
the chaining collection (10 flows, 32 requests) were run with newman against the simulator: all 47 requests
returned 200 and passed their tests. The package's third file, `scenarios/Alarm-API-Scenarios.postman_collection.json`,
is byte-for-byte the same as the baseline collection. To repeat the check against a running simulator:

```bash
npx newman run test-data/postman/Alarm-API-Simulator.postman_collection.json
```

```bash
npx newman run test-data/postman/Alarm-API-Chaining.postman_collection.json
```

The collections' defaults already point at `http://localhost:8000` with the token `demo-token`.

### Endpoints

| Method and path | Purpose | MCP tool |
|---|---|---|
| `GET /health` | Status, version, data counts and the API's data clock (`reference_now`); no token needed | used internally for time windows |
| `GET /assets/search` | Find assets by name, id or type, best match first | `search_assets` |
| `GET /assets/{asset_id}/metadata` | Asset details, related assets, possible alarm codes, alarm statistics | `get_asset_metadata` |
| `GET /alarms` | Alarm events with filters, sorting and pagination | `get_alarms` |
| `GET /alarms/{alarm_id}` | One alarm with duration, minutes to acknowledge and asset summary | `get_alarm_details` |
| `POST /alarms/summary` | Counts and KPIs grouped by chosen fields | `summarize_alarms` |
| `POST /alarms/trends` | Counts per time bucket and the direction of the trend | `get_alarm_trends` |
| `POST /alarms/correlation` | Alarms that fire together and which one usually comes first | `correlate_alarms` |
| `POST /alarms/flood-analysis` | Alarm floods (more than N alarms in M minutes) and their first alarm | `analyze_alarm_floods` |
| `POST /alarms/rationalization-candidates` | Recurring, chattering, stale or mostly unacknowledged alarms | `find_rationalization_candidates` |
| `POST /alarms/priority-score` | Priority score 0-100, band P1-P4 and the factors behind it | `score_alarm_priority` |
| `POST /recommendations/operator-actions` | Likely causes and recommended actions, related assets, history | `get_operator_recommendations` |
| `POST /calculation-code/generate` | Describe a KPI calculation and show its code | `calculate_kpi` (step 1) |
| `POST /calculation-code/execute` | Run the vetted implementation of a generated calculation | `calculate_kpi` (step 2) |
| `GET /analytics/kpi-definitions` | The KPIs and calculation types on offer | `list_kpi_definitions` |

The code shown by `generate` is for transparency only: it is never passed to `eval` or `exec`; `execute` runs a
fixed implementation chosen by the calculation type.

### Authentication

Every endpoint except `/health` requires `Authorization: Bearer <token>`. The token is compared in constant time
(`hmac.compare_digest`); a missing or wrong token gets 401 in the standard error format.

### Trace and client metadata

The API accepts a trace id in either `trace_id` (the Postman collections' header) or `x-trace-id`, keeps it only
if it is a short, safe id, creates one otherwise, returns it in the `x-trace-id` response header and logs it with
the request. `x-client-id` and `x-metadata-tag` are logged too. The connector always sends all three, so one id
links the copilot's question, the MCP tool call and the API request.

### Errors

Every failure uses one format, and validation errors list the fields without echoing the submitted input:

```json
{"error": {"code": "validation_error", "message": "Request validation failed.", "trace_id": "trace-...",
           "details": {"problems": [{"field": "body.lookback_days", "message": "..."}]}}}
```

| Status | `code` |
|---|---|
| 400 | `bad_request` |
| 401 / 403 | `unauthorized` / `forbidden` |
| 404 | `not_found` |
| 422 | `validation_error` |
| 429 | `rate_limited` |
| 503 | `unavailable` |

The simulator never throttles or goes down on its own; the connector's handling of 429, 5xx, `Retry-After` and
timeouts is tested against a mock server instead.

### Pagination

`GET /alarms` takes `page` and `page_size` (up to 200), `sort_by` (`start_time`, `severity`, `asset_id`,
`alarm_id`) and `sort_order`, and returns:

```json
{"data": [...], "pagination": {"page": 1, "page_size": 50, "total_items": 423, "total_pages": 9, "has_next": true}}
```

The connector's `list_all_alarms` follows `has_next` page by page up to a cap and reports whether the result
was truncated; the `get_alarms` tool exposes this as `fetch_all` and `max_items`.

### Time windows

The data is historical, so "now" is the end of the data, not today's date. `/health` reports it as
`reference_now`, and every `lookback_days` (for example "the last 90 days") is measured from it. The MCP server
fetches it once per session.

### Chaining

The chaining collection's 10 flows show how the API is meant to be combined:

| Flow | Steps |
|---|---|
| CHAIN-01 | asset search -> summary -> rationalization candidates |
| CHAIN-02 | flood analysis -> alarms -> summary |
| CHAIN-03 | asset search -> correlation -> alarms -> asset metadata -> recommendations |
| CHAIN-04 | critical-density KPI generate -> execute -> summary |
| CHAIN-05 | asset search -> active alarms -> recommendations |
| CHAIN-06 | stale candidates -> severity summary |
| CHAIN-07 | response-efficiency KPI generate -> execute -> trends |
| CHAIN-08 | motor asset search -> correlation -> summary |
| CHAIN-09 | EastRefinery active alarms -> alarm detail -> priority score -> recommendations |
| CHAIN-10 | nuisance KPI generate -> execute -> rationalization candidates |

The copilot performs the same kind of chains, but through MCP tools. With a model, the agent chooses the steps;
without one, the playbook for the question's intent does. See [architecture.md](architecture.md).

## 2. The Alarm API connector

`connectors/alarm_api_client` is a reusable async client (httpx). The MCP server is its only user in this
project, but it has no MCP dependency and can be used by any Python service.

| Setting | Default | Meaning |
|---|---|---|
| `ALARM_API_BASE_URL` | `http://localhost:8000` | Where the API is (`http://alarm-api:8000` in Docker) |
| `ALARM_API_TOKEN` | required | Bearer token; a `SecretStr`, never logged |
| `ALARM_API_TIMEOUT_SECONDS` | 10 | Timeout per HTTP call |
| `ALARM_API_MAX_RETRIES` | 3 | Retries after the first attempt, for retryable errors only |
| `ALARM_API_BACKOFF_SECONDS` | 0.5 | First backoff; doubles each retry |
| `ALARM_API_MAX_BACKOFF_SECONDS` | 8 | Upper limit for one wait |
| `ALARM_API_CLIENT_ID` | `alarm-mcp-server` | Sent as `x-client-id` |

What it handles:

- **Authentication**: adds the bearer token to every call.
- **Trace propagation**: sends the caller's trace id as `x-trace-id` and `trace_id`, or creates one.
- **Timeouts and retries**: rate limiting, server errors, network errors and timeouts are retried with
  exponential backoff, or after the delay in `Retry-After`. All calls are reads, so retries are safe.
- **Typed errors**: callers branch on the exception class, never on raw status codes.
- **Safe paths**: ids are checked and URL-escaped before they go into a path, so `../x` cannot change the route.
- **Untrusted responses**: a non-JSON response (for example an HTML error page from a proxy) becomes an error
  without being echoed.
- **Call records**: every response carries status, attempts, duration, method and path, which the MCP server
  returns in each tool result and the GUI shows in the trace.

| HTTP result | Exception | Retried | MCP tool error |
|---|---|---|---|
| 400, 422 | `RequestValidationError` | no | `[INVALID_INPUT]` with the problems listed |
| 401, 403 | `AuthenticationError` | no | `[AUTH_FAILED]` |
| 404 | `NotFoundError` | no | `[NOT_FOUND]` with a recovery hint |
| 429 | `RateLimitedError` | yes | `[RATE_LIMITED]` |
| 5xx, network error | `UpstreamUnavailableError` | yes | `[UPSTREAM_UNAVAILABLE]` |
| timeout | `ApiTimeoutError` | yes | `[UPSTREAM_UNAVAILABLE]` |

Tests: `tests/unit/test_alarm_api_client.py` (httpx `MockTransport`: headers, retries, `Retry-After`, typed
errors, paging, path escaping) and `tests/integration/test_client_against_simulator.py` (the real client against
the real simulator, in process).

## 3. The copilot backend API

The GUI talks only to the backend (`apps/backend/copilot/api.py`, port 8080). In Docker the GUI reaches it
through nginx at the same origin (`/api`); in development through the Vite proxy.

| Method and path | Purpose |
|---|---|
| `POST /api/chat/stream` | Ask a question; Server-Sent Events until the answer |
| `POST /api/chat` | The same, as one JSON response (used by tests and scripts) |
| `GET /api/conversations` | Saved chats, latest activity first |
| `GET /api/conversations/{id}` | One chat with every answer |
| `PATCH /api/conversations/{id}` | Rename a chat (`{"title": "..."}`, 1-80 characters) |
| `DELETE /api/conversations/{id}` | Delete a chat and its answers |
| `GET /api/tools` | The tools discovered from the MCP server, with their input schemas |
| `GET /api/health` | MCP connection and tool count, index status, language model, chat storage; HTTP 503 while degraded (same report) |
| `GET /api/live` | Liveness only (`{"status": "ok"}`), for the container health check; checks no dependency |
| `GET /api/examples` | Starter questions for an empty chat |

Request body for both chat endpoints: `{"message": "...", "conversation_id": "conv-..."}`, where the message has
1 to 2000 characters (spaces around it are removed first, so a blank message is rejected) and the id is optional
(omit it for a new chat). Every answer has `saved`: `false` means chat storage failed, so the chat cannot be
opened again later; the GUI then keeps its current address.

The stream sends these events:

| Event | Data |
|---|---|
| `started` | `trace_id`, `conversation_id` |
| `understanding` | the keyword rules' reading of the question (intent and entities; `method` is always `rules`), sent before any model call. With a model, the agent then chooses the steps; the final reading (intent `agent`, or the recipe's intent) arrives in the `answer` event |
| `discovery` | MCP connection, tool count and names |
| `step` | one tool call or document search: arguments, result, Alarm API calls, status, duration |
| `answer` | the full response: answer, evidence, trace, timings, citations |
| `error` | a message and the trace id, if the question failed unexpectedly |

```text
event: started
data: {"trace_id": "trace-f083af1932724e18", "conversation_id": "conv-a14c5ce4373f"}

event: understanding
data: {"intent": "investigate_asset", "asset_query": "Boiler Feed Pump 101", "lookback_days": 90, ...}

event: discovery
data: {"kind": "mcp_discovery", "server": "alarm-management", "connected": true, "tool_count": 13, ...}
```

Errors: 422 for an invalid request (with the problems), 404 for an unknown chat id, 503 with a clear message
when chat storage is unavailable. Every response carries an `x-request-id` header that also appears in the logs.
Browser origins other than the GUI's are refused by CORS (`COPILOT_CORS_ORIGINS`).
